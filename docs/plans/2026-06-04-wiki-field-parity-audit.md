# Wiki field-parity audit: legacy generation vs Lua data pipeline

**Date:** 2026-06-04
**Purpose:** Find every infobox field where the new Lua data pipeline does not
reproduce what the legacy Python generator produced, so nothing silently
regresses at cutover and the override-cleanup pass does not freeze
generated-but-not-yet-migrated data into articles as fake manual overrides.

**Method:** Four layers compared per entity:
- **T (infobox):** `{{#invoke:Erenshor/<Module>|field|X}}` rows in `wiki/templates/*.wiki`.
- **A (accessor):** `FIELD_ACCESSORS` / `FIELD_OVERRIDES` in `wiki/modules/Erenshor/<Module>.lua`.
- **G (Lua data):** the record builders in `src/erenshor/application/wiki_lua/<entity>.py`.
- **L (legacy):** `src/erenshor/application/wiki/generators/sections/<entity>.py` + `templates/*.jinja2`.

Key finding: **Character, Zone, and Stance Lua generators are complete**
(they wire spawn/loot/spell/connection repos and compute everything). **Item,
Spell, Skill, and Quest are not** — Item was built without the
vendor/loot/quest/component repositories, Spell/Skill without the
relationship joins, and Quest barely emits anything.

## Category A — Regression GAPs (legacy generated it; Lua emits no data)

These render in the live wiki today and would disappear at cutover. They also
**poison override cleanup**: a real article value compares against an empty
generated value → classified as a manual override → frozen, stopping future
exports. **Override apply must be blocked for these fields until generation is wired.**

Fixing requires giving each Lua data generator the repositories the legacy
section generator used (via `enriched.sources`).

### Item (7)
| field | legacy source | needed data |
|---|---|---|
| `vendorsource` | `enriched.sources.vendors` | vendor inventory join |
| `source` | `enriched.sources.drops` | loot-table → character join, with drop % |
| `questsource` | `enriched.sources.quest_rewards` | quest reward join |
| `relatedquest` | `enriched.sources.quest_requirements` | quest requirement join |
| `componentfor` | `enriched.sources.component_for` | reverse-crafting join |
| `guaranteeddrops` | `enriched.sources.item_drops` | item drop-pool (fossil-style) |
| `droprates` | `enriched.sources.item_drops` | same pool, with % |

### Spell (3)
| field | legacy source | needed data |
|---|---|---|
| `source` | `enriched.teaching_items` | item → teaches-spell reverse join |
| `itemswitheffect` | `enriched.items_with_effect` | item → has-effect reverse join |
| `used_by` | `enriched.used_by_characters` | character → uses-spell reverse join |

### Skill (1)

|---|---|---|
| `source` | `enriched.teaching_items` | item → teaches-skill reverse join |

## Category B — Key-name / link-render bugs (data IS emitted; accessor wrong)

Data exists in the Lua module but the accessor reads the wrong key, or reads an
emitted **stable key** and returns it raw instead of rendering an AbilityLink.
These are cheap fixes (no new repositories), but they are real display bugs:
the new infobox currently shows blanks or raw stable keys.

### Item (6)
| field | accessor reads | generator emits | fix |
|---|---|---|---|
| `effect` (Activatable) | `i.effect` | `clickEffect` (stable key) | render link from `clickEffect` |
| `worneffect` | `i.wornEffect` | `wornEffect` (stable key) | render link, not raw key |
| `proceffect` | `i.procEffect` | `weaponProc` (stable key) | render link from `weaponProc` |
| `taughtspell` | `i.taughtSpell` | `teachesSpell` (stable key) | render link from `teachesSpell` |
| `taughtskill` | `i.taughtSkill` | `teachesSkill` (stable key) | render link from `teachesSkill` |
| `casttime` | `i.castTime` | (unmapped) | add `("castTime","spell_cast_time")` to field map |

### Spell (1)
| `pet_to_summon` | `s.petToSummon` | `petToSummonStableKey` | render link from stable key |

### Skill (1)
| `target_damage` | `s.targetDamageOverride` | `skillPower` | map/rename so accessor reads `skillPower` |

## Category C — Shown in new infobox, never generated by EITHER pipeline (RESOLVED)

Decisions made with the maintainer, grounded in the game source:

### Character
- `experience` → **generate** as the `BaseXpMin–BaseXpMax` range. This is the
  intrinsic kill XP (game: `Character.cs:776-803` awards
  `round((rolledBaseXp + levelDiffBonus) * ServerXPMod) * BossXp`; the base roll
  is `BaseXpMin..BaseXpMax`). The data is in the export
  (`processor/characters.py:609-610`) but the Lua generator emits only
  `xpMultiplier`. The legacy generator did compute XP-related values
  (`xp_multiplier`, level mod/variance — `sections/character.py:355-386`); the
  base range is the missing piece.
- `class` → **drop the row**. The `Characters` export has no class column (only
  `IsSimPlayer`/`IsNPC`/`IsFriendly`/`IsVendor` flags); the `Classes` table is
  the player-class list for item/spell restrictions, not a per-character
  assignment. Not available for sims or enemies, so it cannot be generated;
  remove `class` from the Character template and module.

### Quest — **deferred**
`location`, `prerequisite`, `level`, `itemsrequired`, `items`, `previous`,
`next` stay ungenerated for now. Quest infobox completeness is out of scope for
this pass. The override-apply gate (below) still applies so these are never
frozen as overrides.

### Item spell-derived fields — **match the game (keep)**
`dps`, `casttime`, `duration`, `cooldown`, `manacost`, `spelltype`, `skilltype`,
`effects`, `buffgiven`, `produces`. These are NOT removed. The game shows an
item's click/proc/worn spell detail in the item tooltip (`ItemInfoWindow.cs`),
so the wiki item tooltip must too (it does, via `Item/Tooltip.lua`'s
`spellDetails`). The infobox links to the ability (`effect`/`proceffect`/
`worneffect`/`taughtspell`/`taughtskill` → AbilityLink, Category B). Specific:
`dps` → compute from damage/delay (weapon metric); `produces` → map to the
emitted crafting `rewards`. The rest are honored where data/tooltip provide them;
nothing is pruned deferentially.

**Item tooltip vs game (verified `ItemInfoWindow.cs:661-805`):** the item proc/
click/worn detail matches the game row-for-row, with three deliberate additions
the game's `LoadSpellDetails` omits — `Healing` (targetHealing), `Shield Amount`
(shieldAmount), and `XP Bonus` (xpBonus). These are kept as intentional
enhancements (a healing-proc item should show its healing); decision confirmed
with the maintainer. The shared-primitives refactor introduced zero drift
(byte-identical output verified on the harness).

## Category E — Spell and skill tooltips (DONE)

Implemented in Milestone 10b: `Module:Erenshor/Spell/Tooltip`,
`Module:Erenshor/Skill/Tooltip`, `{{SpellTooltip}}`/`{{SkillTooltip}}`, and the
shared `Module:Erenshor/Ability/Common`. The item tooltip (`Item/Tooltip.lua`)
faithfully reproduces `ItemInfoWindow.cs`. The game renders the new tooltips in:
- **Spell:** `SpellbookSlot.cs:150-275` — duration line → Spell Type → Mana Cost
  → Damage(`/tick`) → Cast Time → Cooldown → Resist Type (colored) → flags
  (Lifetap/Group/Stun/Charm/Root/Taunt) → applied status effect → nonzero stat
  mods (`+green`/`-red`) → SpecialDescriptor.
- **Skill:** `SkillbookSlot.cs:146-156` — title `Name - Activatable|Passive`
  (Activatable when `TypeOfSkill != Innate`), body `SkillDesc`, or the
  `Change Stance` + stance name/desc variant. No numeric block — authoritative
  reason skills have no stat block.

Both surfaces reuse the `item-tooltip-*`/`item-spell-*` CSS for visual parity,
with link conveniences (applied status effect, stance), and share rendering
primitives via `Module:Erenshor/Ability/Common` (Item/Tooltip refactored onto it,
verified byte-identical).

**Layout refinements:** the standalone spell/skill tooltips add the
`item-spell-details-spacer` so the title centers against the fixed-width icon,
and an inline `border-top: 2px solid #d0d0d0` on the root so they read as a
complete frame. The embedded item proc/worn detail keeps `border-top: none`
(it sits under the item tooltip's divider), so only the standalone roots carry
the inline border.

**Known gap — tooltip CSS is not repo-owned.** The `item-tooltip-*` /
`item-spell-*` classes live only in the live wiki's `MediaWiki:Common.css`,
synced down to the gitignored `wiki-dev/interface/MediaWiki/Common.css` for the
harness. The new tooltips deliberately reuse those existing classes (so no new
live CSS is required) and inline the one new rule (the standalone border) in the
module, which is why no class-based stylesheet change was made. If future tooltip
styling needs new classes, the wiki CSS must first be brought under repo
ownership; until then, prefer inline `mw.html:css(...)` for module-local styling.

## Category D — Intended manual (no action)

- `imagecaption` — every entity. Per-article human caption.
- `othersource` (Item) — explicitly manual (sources that don't fit other categories).
- `level` (Zone) — not in game data; `pages/zones.py` preserves it via `FieldPreservationHandler`.
- Skill stat block (`hp/mana/ac/str/...`) — skills have no such stats in the game
  (`Skills` table has only `SkillPower`/`PercentDmg`/`DamageType`/`Cooldown` + link
  keys); the in-game skill tooltip shows no numeric block. Not a gap.
- `class` (Character) — dropped entirely (no per-character class in the export); see Category C.

## Override-cleanup safety gate

Until Category A (and the Category B render bugs) are closed, the override
**apply** path must refuse to remove any field whose generated value is empty
because the data isn't generated yet. Otherwise it converts generated content
into permanent fake overrides on ~1300 item articles and every character/spell
page. The review (report-only) command is safe to keep running; only apply is gated.
