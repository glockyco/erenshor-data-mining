# Design

## Context

See `proposal.md` for motivation and `adopt-data-backed-wiki/design.md` D1-D3 for the publishing boundary. This change is planning only.

Read-only observations from the current source, clean/raw databases, saved articles and production API on 2026-10-17:

- `CharacterSectionGenerator.generate_template` in `src/erenshor/application/wiki/generators/sections/character.py` writes mana, seven attributes, XP multiplier, placement level modifiers and variance. `wiki/templates/Character.wiki` displays none of these. It declares class and Base Experience rows, but `_build_character_template_context` supplies neither. Production `Template:Character`, revision 65385, has the same deficits and is parameter-only.
- `CharacterListener.CreateCharacterRecord` exports `Stats.CharacterClass.name`, BaseMana, seven base attributes and BaseRes. The clean `characters.class_resource_name` column exists, but `Character` lacks it and `CharacterRepository.get_characters_for_wiki_generation` does not select it. The repository does select base XP and effective HP/AC/resistance fields. This is a projection gap, not missing game data.
- Class is not part of `_dedup_key`. A read-only query found a wiki-visible training-dummy group with both null and non-null class values. A representative's class is not automatically every copy's class. Preserve member identity when presenting this new field.
- `CharacterListener` exports `BaseXpMin = level * 6` and `BaseXpMax = BaseXpMin + level * 5`. The shipped `Character.Start` initializes `xp` to level times six. `Character`'s death branch adds a player-level-dependent bonus, server XP multiplier and BossXp. `NPC.Start` raises BossXp below two to two at level 40 or above, while the death branch changes zero to one. Thus the exported min/max must not be described as a random base XP roll, and the legacy zero-to-one formatter does not represent the level-40 reward multiplier. `StartComponentsListed` and `StartComponentsByFileId` currently track NPC, Stats and TestDummy, not Character. Correct initialized XP needs that missing component-order input as well. These are source-confirmed observations, not runtime experiments.
- `npc_level_bounds` applies the level-one floor and below-35 variance after placement modifiers. `processor/npc_spawn.py` and `processor/characters.py` already implement component start order, effective HP/AC/resistance calculations and dummy behavior. `wiki_lua/treasure.py` publishes complete player-level guardian scaling and chest waves. None of these formulas belongs in Lua.
- `SpawnPointRepository.get_spawn_info_for_character` supplies positions and furniture but not night, stop quests, protector and trigger requirements. `CharacterRepository.get_zone_roster_spawns` has a richer condition projection. Conversion must share the common clean spawn projection used by WikiOverviews and the canonical source owner, not reproduce the older incomplete summary query.
- The current clean database has 1,254 character rows, including 361 coordinate-bearing keys. The raw database has 1,421 rows, including 362 coordinate keys and 166 SimPlayer rows. The wiki-visible dedup representative query yields 931 roots on 873 pages. These are observations, not fixed acceptance counts.
- `StableKeyGenerator.ForCharacter` embeds object name, scene and two-decimal position for scene objects. `CharacterStableKeyResolver` adds duplicate suffixes by first encounter. `CharacterListener` writes prefab asset GUIDs or `scene:<scene name>:<GameObject local file ID>` into raw `Guid`, and the processor preserves this as clean `guid`.
- All current raw GUIDs are populated and unique. For example, `character:a highwayman raider (1):elderstone:-732.18:-51.70:194.52` has `scene:Elderstone:1665`. The actual serialized Elderstone scene has GameObject `&1665` with its component references at lines 28559-28588. The scene meta GUID is `b9c86eeea0a52e749952182c30ae840b`. Raw Guid stores the scene name, not that meta GUID. This is a native object anchor, not a name-based match.
- The only retained database backup is the same build. Joining that raw snapshot to current raw rows by Guid found no changed key, so there is no observed moved-spawn example or cross-build stability proof in the available corpus. AssetRipper regenerates a Unity project. Neither generated meta GUIDs nor local file IDs are established eternal game identities. `AuxiliaryFiles/path_id_map.json` exists, but it is not consumed by the exporter and the inspected data does not prove a scene-object continuity mapping. Do not infer a new identity scheme from its filename.
- The native item reconciler `reconcile_converted_item_page` returns original bytes when membership is unchanged, adds compact calls for additions, and rejects removals for lifecycle handling. It cannot interpret a moved coordinate key as continuity. `CompanionProof` binds old generated bytes to an actual checkpointed bot revision. `apply_guarded_edits` already persists rollback text before any edit and checkpoints successful revisions.
- Production reports `Module:Erenshor/Data/Characters` missing. New Character data can therefore use that title only after a fresh existence check. Production Jethro, revision 62936, is an authored unkeyed Character call with Sim type, an old screenshot title, caption, faction and class plus prose. Aethaya is missing. The live Simulated Players article distinguishes fixed people from randomized names. Ordinary NPC conversion must leave Jethro and similar authored pages alone and must not resurrect randomized-name pages.

## Goals / Non-Goals

The data contract preserves copy-specific conditions and identity while presenting short labels and grouped details for ordinary visitors. It fixes the known hidden rows instead of hiding them behind a template rename.

This change does not redesign encounter classification, select item sources independently, convert quest pages, migrate dedicated SimPlayer pages into ordinary NPC data, change map protocol versions, introduce Lua queries, or launch a game. Any future runtime validation follows the combat-evaluation and session-cleanup rules. Public text does not expose pipeline enums, lineage proofs or an explanatory caveat wall.

## Decisions

### D1. Public root and field ownership

Use `{{CharData|stablekey=character:...}}`. `Template:CharData` calls `Module:Erenshor/CharData.render`. An unknown, missing, wrong-kind or duplicate identity shows a short diagnostic and `Category:Character data calls with invalid identities`. It never resolves by name or silently falls back to copied facts. A shared page has one call per canonical wiki-visible dedup representative, in the existing scene then descending-level then key order. The call resolves only its own record and required relation shards.

| Input | Owner and behavior |
|---|---|
| `stablekey` | Required identity, not an override. |
| Name, tier, class, faction, kill reputation, abilities, stats, level bounds, XP, loot, spawn conditions, lifecycle and build | Data. No article parameter replaces these facts. |
| Canonical render and screenshot file titles, summon/chest image kind | Data, using `picture_file_title` and approved image/catalog inputs. |
| `imagecaption` | Editor. Exact existing value remains visible with its root. |
| `location` | Editor. Exact landmark description remains visible beside canonical locations. |
| `zones`, `coordinates`, `respawn` | Editor fallback notes. Keep their exact values. Display a fallback only when the corresponding canonical field is absent. Never replace known data. A retained nonempty field covered by data places the page in `Category:Character location notes covered by game data` for review, not silent deletion. |
| `render`, `screenshot` | Optional additional editor picture titles, not replacements for canonical pictures. Keep unproven existing values byte-for-byte and include existing files in the same gallery without duplicate titles. Remove a legacy value from the compact call only when a native publication checkpoint proves it was the bot's generated picture value. |
| Prose, headings, galleries, interface pictures, strategies, links and categories outside a proven generated region | People. Preserve exact bytes. |

The seven optional editor fields above are the complete allowlist. Unknown nonblank legacy parameters are inventoried and must have a disposition before conversion. Never discard an unexplained parameter because generation currently owns its name. Unsupported parameters on a future CharData call do not override data and add `Category:Character data calls with unsupported parameters`. All tracking categories have repository-owned instructions explaining the editor action.

Generated category ownership needs the same proof boundary as companions. Data emits Characters, Enemies, Elites, Bosses, Chests, Vendors and actual zone page-title categories in main namespace. A shared page gets the union. Remove old explicit category text only when checkpointed generation proves ownership. Otherwise keep it unchanged and report duplicates or contradictions for review. Category membership must not depend on editor fallback zones or an overridden type string.

Legacy `Template:Character` stays compatible, parameter-only and without Lua. A compatible parameter presentation helper may be factored out, but the new CharData surface must actually show the previously missing rows. Do not route through the legacy template and inherit its omissions.

### D2. One Python fact projection, complete visible stats

Extend the existing clean Character projection and model to carry class references, native identity provenance and member-specific fact variants. Resolve playable class labels with the existing class display/link catalog. Preserve non-player class identity as plain text when no article target exists, rather than fabricate a class page. Null class means absent, not a guessed class. Where relevant members disagree, show the distinct class or stat variants with their actual copy/location conditions. Never select the lexicographically first member's new facts and call them universal. Do not change dedup identity solely to avoid handling variants.

Reuse the existing NPC initialization helpers for all derived values. Move any reusable computation out of the legacy section builder only into a single Python owner. Add derived initialization/XP fields to the clean model rather than calculate them in Lua. Extend the existing CharacterListener start-component inventory and `npc_spawn` order model to include Character so initialized XP is grounded in the level its own Start sees. Preserve the existing NPC/Stats/TestDummy behavior. Validate this added order-sensitive case in the actual Unity/game host during implementation before claiming exact initialized XP, using controlled dummy and ordinary prefab/scene cases and regular shutdown. Keep designer BossXp for encounter tiering distinct from the effective reward multiplier. Add or extend shipped-method code facts for the exact zero-to-one and level-40 reward branches and the player-level bonus semantics. Use those facts through the existing initialization model. The source-confirmed correction is not a license to change tiers from runtime BossXp.

The infobox has concise identity, location and encounter rows. A visibly available Stats group shows health, mana, AC, Strength, Endurance, Dexterity, Agility, Intelligence, Wisdom, Charisma and the four resistance ranges. Zero is displayed as zero when known. Unknown is omitted without substituting zero. Distinguish base exported attributes/mana from initialized effective health, AC and resists with group labels, not repetitive disclaimers.

Show Base Level, the actual placement/variance level range and XP multiplier. Show Base Experience from its actual initialization value before the player-level bonus and multipliers. The exported maximum is not a random-roll endpoint. A short label such as `Base experience` and `XP multiplier` plus the existing Leveling link suffices. If start-order or player-level dependence changes the value, Python emits a supported range or scaling row tied to that condition. Never claim the whole payout is fixed. Keep the underlying raw XP inputs and the conditional reward projection available to editor modules.

Level bounds use `npc_level_bounds` separately for each modifier/group combination, including levels 1, 34 and 35. Do not call it once on a merged minimum that crosses the level-35 boundary. Effective stat ranges reuse `npc_spawn` with the actual initialization order and relevant levels, not a new approximation based on the displayed range. Keep training-dummy hand-set AC behavior as the existing concise note. Read `can_be_damaged` and release conditions from their shared clean owner, not initial invulnerability or named-character exceptions.

Treasure chests show no combat stat or XP block. Scaling guardians show `Scales with the player's level` and reuse the complete `TreasureGuardianStats` data/render surface once. They do not show misleading fixed prefab values. A native checkpoint proves ownership before the old generated companion is removed. An editor's independent scaling table or companion remains untouched and blocks automatic deduplication when ownership is uncertain.

### D3. Loot and location relations are shared facts

Consume CanonicalSources' canonical item source/use relations. The character renderer requests the character/copy-keyed slice of these relations through the established Python composition boundary. It must not call an old independent character-loot selector to rebuild chances, re-expand the global pool, or query item records in Lua to discover reverse edges.

Preserve relation IDs, source-copy identity, item identity, probability kind/denominator, quantity, guaranteed pool/roll count, equipment visibility, unique-held restriction, quest and furnishing conditions, time restrictions and level bounds. Render the actual guaranteed-pool semantics and overall chances. Same-page same-label variants can share a concise row only when their conditions remain visible and chance ranges are truthful. A common-world-item swap remains one world-drop-like source, never one invented enemy-drop edge per NPC. Generic global rolls are not copied into individual enemies' guaranteed or ordinary drops. Link the common source view once when applicable.

Use the common clean spawn/condition projection already needed by zone rosters, item provenance and guide exports. Extend that owner if the article needs missing fields, with no second eligibility selector. Serialize ordinary/direct/trigger/event/chained placements with zone and optional coordinates, spawn chance, base respawn, night, required/completed/stopping quests, protector/release conditions, trigger item/mode and furnishing room requirements. Unplaced but source-backed summons or events remain valid characters. Summons show the real summoning ability and no fabricated fixed location or respawn. Treasure locations stay possible dig-site zones rather than coordinates of a hidden prefab.

A Reliquary furnishing is available only in a room furnished with its relevant set. An initially invulnerable quest-released enemy remains listed with that condition. Unknown position is not `(0, 0, 0)`. Only actual mapped, usable placements generate map links, using the map's existing supported selectors. Do not add a name-only map link for a summon, unplaced prefab or editor fallback zone. Keep conditional but mapped spawns visible and label the condition briefly. The renderer lists multiple real placements in a compact locations group rather than discard them because the old coordinate summary accepted only one location.

### D4. Galleries and authored SimPlayer boundary

Show the canonical render first and screenshot second, plus any retained additional editor picture titles. Preserve root captions, standalone galleries, per-file captions and all surrounding prose. Check file existence before producing gallery lines. One existing file renders without tabs. Missing files create no broken-file link, and the appropriate Character, Summon or Chest image tracking category is emitted only when no eligible file exists. Full file titles come from the shared filename helper or exact editor input. Never synthesize screenshot uploads or rename an editor's old file in this conversion.

Keep the processor's SimPlayer exclusion. Current authored dedicated pages such as Jethro keep their legacy Character calls, faction/class/captions and prose without being marked broken or ordinary NPCs. Inventory them as `authored_sim` dispositions separate from generated characters. A future dedicated Sim data contract must be explicitly typed and sourced from authored/fixed Sim assets. Do not populate it from a randomized name list or from the ordinary NPC table. This change neither creates that separate contract nor blocks ordinary NPC completion on converting those intentionally manual pages.

### D5. Bounded, additive data modules

After checking the live namespace again, publish `Module:Erenshor/Data/Characters` as an index and deterministic stable-key hash-prefix child shards. If that title acquires an existing incompatible consumer before implementation, use a new versioned title and update the new reader instead of changing its structure in place. The index maps every supported character key to its representative/shard explicitly. Historical key aliases are not inserted to conceal identity changes.

Each representative record includes canonical identity/page, member keys, scalar/stat variants, canonical pictures, class/faction references, initialized level and XP data, ability references, lifecycle/build references and references to the required relation shards. A narrow `CharacterRelations` index/shards may carry reverse character relation IDs when the canonical item data does not already provide an efficient compatible slice. This is serialization of the canonical owner, not another source model. Reuse complete `Data/TreasureGuardians`, Links, Build and item data without changing their structure. Split location or detail shards when measured budgets require it. No module scans every character or loads every item to render one root.

Use `wiki_lua/lua_writer.py` and the existing generation/dependency/page-size gates. Stable bucket subdivision is deterministic and must not change based on database enumeration order. Enforce configured UTF-8 page bytes before publishing any page. Never solve limits by dropping stats, relation conditions, pictures or locations.

Use the item conversion's native actual-host comparison and limit-report mechanism. Build a corpus from all current generated identities and all live Character users with continuation, not only saved pages or a fixture. Include the largest record, most locations, most loot variants, longest conditions, multi-root pages, image existence cases, scaling guardians and pages with many semantic links. Parse with actual generated-scale data in local MediaWiki and record limitreportdata, Lua CPU/memory where exposed, expanded/post-expand sizes, expensive function count, loaded shard count and bytes. Query each host's actual enforcing limits. Require at least 25 percent headroom on measured limits. Unsupported metrics are reported honestly and cannot be invented. Production comparisons with missing staged dependencies are provisional and cannot approve a cutover.

### D6. Proven movement lineage, not inferred aliases

Store a bot-owned conversion/update inventory under the variant wiki run artifacts, not in article prose. Each record binds build and raw/clean/source artifact hashes, old representative, raw member keys, native GUID kind/value, source scene artifact identity/hash, native GameObject local ID, canonical page membership, revision/hash and owned editor field hashes. This is publication evidence, not a new Lua-facing identity scheme.

Match unchanged exact keys first, while checking that retained native provenance has not contradicted the key. Coordinate movement candidates are established at raw member level, before dedup representative selection:

1. Require two identified source snapshots, unique nonempty native GUIDs on both sides, the same native scene object identity and unambiguous membership of the old and new rows. `scene:<name>:<id>` equality is only a candidate. Validate that each GUID resolves to the actual scene GameObject and linked Character/Stats/NPC component IDs in its respective retained serialized artifacts.
2. Accept an automatic movement proof only when the retained native object/component graph is continuous and the serialized diff proves a transform-only placement change, with unchanged non-transform object/component identity and contents. Record the before/after transform, component-reference graph and source hashes in the proof. A controlled fixture derived from the real Elderstone object must show that moving its transform changes the exported coordinate key while retaining that anchor. This fixture proves the narrow operation, not arbitrary cross-build stability.
3. Any re-rip, changed scene identity, recycled local ID, added/replaced component, changed non-transform object content, missing artifact, duplicate GUID or inability to establish native continuity is unknown. A mapping correction may identify continuity only with an explicit reviewed reason and native evidence. Do not use display name, suffix stripping, nearest coordinates, similar stats or a fabricated alias to fill the gap. Do not promote generated scene meta GUID equality to proof across unrelated rips.
4. Lift proven member matches to representative membership using the actual old/new `character_deduplications` and wiki-visible representative rules. Exactly one old root must correspond to exactly one new root with the same complete relevant member lineage. A changed minimum representative with unchanged members is a membership identity replacement, not a new character. Splits, merges, extra/lost members and page moves are explicit reviewed lifecycle/membership operations, not automatic transform continuations.
5. For a proven one-to-one replacement on the same page, edit only that root's `stablekey`, retaining every editor value and all non-owned bytes. Persist the proof ID and both keys in the native guarded plan/manifest sidecar. Never create a permanent old-key Lua alias. Group the new data publication before the guarded key replacement, retaining old publication bytes during rollback.

The existing membership reconciler rejects a removed key. Keep that safe default. An unknown old-to-new relation leaves the live call and page unchanged, blocks reconciliation for the affected page and records both candidates for reviewed lifecycle handling. It must not silently append a duplicate root, retire the old page or transfer captions to a same-named character. A full update cannot claim clean reconciliation while these cases are unexplained. Missing historical data needed for a proof is not a reason to invent a proof.

### D7. Native conversion, production acceptance and rollback

Extend the native migration machinery introduced for items through the parent's shared neutral seams. Reuse `GuardedPageEdit`, `apply_guarded_edits`, production text comparison, measured limits, manifest checkpoints and rollback. Do not fork a Character HTTP client or complete migration engine, and do not generalize item quality/tooltip logic into this renderer.

Inventory every current eligible root and all actual live legacy/new Character calls, including nested, namespace-qualified, multi-root, manual and historical pages. Record exact editor values, complete outside-region bytes, category and companion proof, source/corpus hashes and fetched revisions. Native unique legacy matching can identify an unkeyed ordinary root, but ambiguity, duplicate parameters, unknown factual values and unmatched roots require dispositions. Authored Sims and manual legacy calls have explicit retained dispositions, not omitted inventory rows.

For each eligible page, convert all eligible roots in one candidate text. Replace only the identified root and checkpoint-proven bot companions/categories. Preserve all prose and editor markup verbatim, even between a root and companion. `TreasureGuardianStats` is the character-specific generated companion requiring proof. Keep manual tables, vendor-stock view calls and unrelated template calls. If ownership cannot be proven, retain content and block duplicate generated output until reviewed. Save rollback bytes before the first write and every successful new revision afterward.

Compare every ordinary character page on production using `action=parse` text parses of legacy and converted text under the actual title. Record full visible text, semantic links, categories, images, exact outside-region hashes and limit reports. Review every difference, with intended additions of missing stats, accurate XP and conditions separate from regressions. Neither a feature-selected sample nor a nonempty parse establishes completeness. Existing production dependencies must be real before this comparison is final.

Browser-check locally on the actual MediaWiki host using full data. Cover friendly/vendor, enemy/elite/boss, chest, summon without placement, quest-released enemy, furniture, treasure guardian, training dummy, missing/one/two/custom pictures, authored Sim compatibility and a shared multi-root page with distinct captions. Exercise narrow/desktop layout, gallery selection and map links. Capture screenshots for local review before live approval. There is no new runtime game UI in this change.

Publish new data, then renderer/styles/templates/categories through a full reviewed repository-page dry run and explicit approval. Next obtain a separate canary article approval, convert it, parse it, exercise manifest rollback and verify exact original text and unaffected later edits. Reapply only with fresh approval. A new full broad dry run against fresh revisions needs separate approval. An interrupted write batch must be completed or rolled back before another pass. A changed/deleted article is a conflict, never an automatic force write. Keep old bytes and reader dependencies for rollback throughout the agreed window. Administrator deletion of old wiki pages requires a reader inventory including editor modules and legacy users.

### D8. Cutover and last-type cleanup gates

After a complete approved broad pass, `wiki generate` creates compact new Character stubs and reconciles existing pages only for identity membership changes, including the proven key replacement above. A stats, loot, location-coordinate or build update with unchanged identity membership makes no article edit. An existing call with editor fallback notes is not rewritten just because data now covers it. Tracking categories surface that state. Store no full-article fallback mode after Character cutover.

Delete `CharacterSectionGenerator`, `templates/character.jinja2`, Character-only assembly/formatting and merge/validation branches only when all generated identities have reviewed dispositions, all corpus/browser/limit checks pass and canary rollback is exercised. Preserve shared repositories, NPC stat/level helpers, treasure renderers with remaining readers, the legacy Character parameter template and native guarded deploy/rollback.

Character is the final planned type, but order is not proof of completion. Shared removal requires accepted receipts for Item, Stance, Spell, Skill, Zone and Character conversions, plus completion/disposition of the earlier overview refresh consumers. Quest articles are manual and their panels do not authorize keeping a generated Quest full-article path. Search the actual callers and remove obsolete generated Quest machinery if present, not the legacy manual Quest template.

Only after all those gates remove `field_preservation.py` and surrounding obsolete merge passes, all remaining article Jinja templates, the Jinja dependency if unused, full-article generation orchestration and obsolete refresh-only validators/tests/options/docs. Migrate every real remaining stub/membership caller to the native path first. Keep guarded edit/deploy, manifest-driven rollback and retained rollback source bytes. Compatibility is continued legacy template rendering, not retaining a second obsolete Python refresh engine. Update the authoritative parent plan and existing Game Data/template guides in place as each actual cutover lands. Do not duplicate field inventories in permanent repository documentation or carry a finished one-time migration runbook indefinitely.

## Risks / Trade-offs

- Native GUIDs are useful evidence but not a cross-build identity guarantee. Automatic continuity is deliberately narrow. Genuine game updates that replace native objects need reviewed lifecycle dispositions rather than false certainty.
- New class and XP fields expose old projection and initialization deficits. These must be repaired once in Python/clean data before the renderer ships, not patched in Lua or hidden again.
- More complete spawn and loot data increases parse cost. Deterministic sharding and measured host budgets are required, with no completeness loss to meet them.
- Preserving unproven picture/fallback/category bytes may leave reviewable duplicates. Exact editor preservation takes precedence over guessing bot ownership.
- No material editorial choice remains open for implementation. The visitor-facing arrangement and labels require the usual screenshot review, and publication timing remains a separate explicit approval. No runtime or cross-build movement result is claimed by this planning work.
